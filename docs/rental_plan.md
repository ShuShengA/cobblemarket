# 精灵租赁系统计划

> 状态：方案已拍板（2026-09-09 讨论定稿），待排期
> 定位：玩家把精灵出租给他人换取租金，租客临时获得使用权。**第一优先级：租赁期间精灵绝不丢失、绝不复制。**
> 来源：基于桌面草案 `租赁功能.txt` 整理。相对草案的改动：归还流程、租赁栏位、数据存储按模组实际情况重写；**UI 改为与精灵市场融合**（不单独做租赁市场界面）；**租期改为房东设上限、租客选**。

## 核心原则

- **服务端持有权威快照**：出租瞬间把精灵完整 NBT 存进服务端，租客手里那只降级为"可删除的临时实例"。归还永远以快照为准，不依赖任何人在线。
- **快照先落盘，再从房东处移出**：两个动作在同一 tick 完成（沿用现有节流落盘，要么一起进存档、要么一起丢）。
- **删除是归还的必要动作**：租客那只删不干净 = 复制。删除优先，删不掉留标记，标记持久化。
- **不拦截无害操作**：装备携带物、放进 PC 都不拦（快照兜底 + 到期扫描能覆盖）。

## 与现有系统的关系

| 系统 | 关系 |
|---|---|
| 精灵市场 / 拍卖 / 求购 | 租赁中的精灵**不能**上架（三个入口都要加"租赁中"检查）；一只精灵同时只能处于待租/租赁中/在房东手里之一。精灵市场同时承担租赁市场的展示（见 UI 界面） |
| 待领取 | 归还的精灵统一进房东待领取（复用现有机制，无需担心 PC 容量） |
| 货币 | 复用 `CurrencyHandler` 主市场货币后端，**不做**草案里的"四种货币" |
| 费率 | 租赁税并入现有费率体系（照市场手续费的做法），收入计入系统账户 |
| 交易历史 | 租用/续租/归还写入现有交易日志 CSV，不另起账本 |
| 金融系统 | 租金走现金；**不支持**消费贷支付（与拍卖出价同等处理） |
| 面对面交易 | 租赁中的精灵不能参与（`TRADE_EVENT_PRE` 拦截） |
| 管理面板 | 新增「异常记录」入口（仅 OP，见下文「异常记录」节） |

## 数据模型

新增 `RentalState`（PersistentState + .bak，照 `FinanceState` 模式），三张表：

```
listings: Map<String, RentalListing>   待租池
leases:   Map<String, Lease>           租约
pendingDeletions: Map<UUID, List<PendingDeletion>>   租客 → 待删除
```

- `RentalListing`：挂单 ID、房东 UUID、精灵完整 NBT、精灵 UUID、日租金、到期去向、上架时间
- `Lease`：租约 ID、挂单 ID、房东 UUID、租客 UUID、**精灵 UUID**、**出租时快照 NBT**、日租金、开始/到期时间、到期去向
- `PendingDeletion`：精灵 UUID、来源租约 ID、房东 UUID（仅用于告警追溯）

精灵 NBT 内嵌存储，照 `MarketListing.pokemonNbt` 的现成做法（不是引用 PC 仓库）。挂单被租出后从待租池移除，状态由租约承载；到期"留在市场"时从租约快照重建挂单。

## 出租流程（房东）

1. 在**选择上架精灵界面**选中自己的精灵 → 点「出租」→ **二次确认窗口**（「上架」无二次确认）
2. 窗口内设置：**可租天数上限**（落在服主配置的最小/最大租期之间）+ 日租金 + 到期去向（回到自己 / 留在市场）
3. **自动取下携带物**：背包有空位直接放入并提示；满了进房东待领取并提示
4. 生成快照（完整 NBT，保留原 UUID）写入 `RentalListing`
5. 精灵从房东处移出 → 进入待租池（与市场挂单同款：服务端只存一份 NBT）
6. 第 4、5 步同 tick 完成

## 租用流程（租客）

1. 在**精灵市场**里浏览（租赁精灵与出售精灵同列表，图标区分）
2. 点租赁精灵 → **租赁确认窗口**：选租期（服主下限 到 房东设的上限之间）+ 总价（日租金 × 天数 + 税）+ 确认
3. 确认支付 → 扣款 → 精灵从待租池实例化到租客队伍（队伍满则进 PC）
4. 写入 `Lease`（含出租时快照）
5. 通知双方

## 租赁期间

**租客可以做**：放入队伍战斗、骑乘、跟随、装备自己的携带物。

**拦截清单**：

| 操作 | 手段 | 必要性 |
|---|---|---|
| 玩家间交易 | `TRADE_EVENT_PRE` | **必须**——唯一已知的"精灵离开租客账号"路径 |
| 上架 / 拍卖 / 求购 | 模组三个入口加检查 | **必须** |
| 放生 | `POKEMON_RELEASED_EVENT_PRE` | 建议（不拦不会复制，但违反设计意图） |
| 进化 / 改昵称 | `EVOLUTION_ACCEPTED` / `POKEMON_NICKNAMED` | 建议（快照会回滚，拦了玩家才不白费道具） |
| 装备 / 取下携带物 | — | **不拦** |
| 放进 PC | — | **不拦**（Cobblemon 无对应事件；快照兜底后无必要） |

统一走一个检查函数 `RentalGuard.isRented(pokemonUuid)`，各挂点第一行调用。

**数据回滚**：租赁期间的经验、等级、技能、EV 等变化，归还时全部以快照为准丢弃——归还的永远是出租时的状态。

## 归还流程（核心）

到期由服务端自动执行，不依赖房东或租客在线。

**分支一：租客离线**
- 从快照恢复精灵 → 房东待领取（或重建挂单重新上架）
- 给租客打「待删除」标记（持久化）
- 租客下次登录时执行删除，直到删掉为止

**分支二：租客在线且不在战斗中**
- 在租客队伍 + PC 里按 UUID 找那只精灵
- **找到** → 取下其携带物（→ 租客背包，满则租客待领取）→ 删除 → 从快照恢复给房东
- **找不到** → **告警 OP + 暂缓归还**，记入异常队列。宁可让房东多等、OP 介入，也不要凭空变出一只

**分支三：租客在线且正在对战中**
- 不回收，等战斗结束再走分支二
- **不做"超时强制回收"**（草案里的 10 分钟强收会重演 BattleGuard 漏洞：战斗中抽走队伍精灵 → 模型消失/队伍补员）
- 超过阈值（如 1 小时）仍未结束 → 告警 OP

**待删除的执行**：租客每次登录时扫描队伍 + PC，按 UUID 删除；删不到则告警（此时复制已成事实，需 OP 介入）。携带物取下规则同上。

## 续租 / 提前归还 / 手动下架

- **续租**：到期前（阈值进配置，草案写"剩余 24 小时"）可发起，租客选续租天数（同样在房东设的上限内），支付后延长到期时间；未续租则到期自动归还
- **提前归还**：租客可主动归还，租金不退，走正常归还流程
- **手动下架**：精灵在待租池时房东可下架 → 进房东待领取（携带物随精灵走）
- **OP 强制下架**：任何状态都可强制下架，终止租约，精灵进房东待领取，租金不退

## 配置项

| 配置项 | 默认值 | 说明 |
|---|---|---|
| 租赁总开关 | true | |
| 租客最大同时租赁数 | 3 | |
| 房东最大同时出租数 | 5 | |
| 最小 / 最大租期 | 1 天 / 7 天 | 全局边界，房东设的可租上限必须落在区间内 |
| 租赁税 | 5% | 并入费率体系 |
| 可租精灵类型 | 全部 | 可限制普通/闪光/传说等 |
| 续租窗口 | 24 小时 | 剩余租期小于此值才可续租 |
| 异常战斗告警阈值 | 1 小时 | 战斗未结束多久后告警 OP |

**蛋不参与租赁**（不能战斗，租赁无意义）。

## UI 界面

**不单独做租赁市场界面，与精灵市场融合**（2026-09-09 拍板）：

- **精灵市场（`MarketScreen`）**：出租中的精灵与出售精灵同列表展示，行信息加租赁图标区分（图标由用户绘制）
  - 筛选面板加三态「不限 / 仅租赁 / 仅出售」，默认不限（混合显示）
  - 按价格排序时售价与日租金量级差异大、租赁精灵会沉底——玩家可先选「仅租赁」再排序，不做特殊处理
  - 点击分叉：出售精灵 → 现有购买确认弹窗；租赁精灵 → **租赁确认弹窗**（租期选择 + 总价 = 日租金 × 天数 + 税 + 确认，照 `AdminAuctionScreen.openCancelDialog` 黄金模板）
  - 服务端下发统一的列表项结构，带 `isRental` 标记；筛选走服务端过滤
- **选择上架精灵（`SellSelectScreen`）**：顶部按钮排加「出租」按钮。现有排布已排满（闪光30 | 公母24 | 属性58 | 价格56 | 上架44 | 特训60 = 272px），开工时先算宽度再排版
  - 「上架」**无**二次确认（本来就要先选中精灵）；「出租」**有**二次确认窗口
- **我的（`MarketScreen` 的「我的」筛选）**：租赁中的精灵、出租中的精灵都归入「我的」筛选，不单独做「我的出租」「租赁中」界面
- **管理界面（OP）**：全服租约列表 + 强制下架 + 手动终止

## 异常记录（通用系统）

租赁异常**不能只发聊天框**——OP 不在线就漏了；将来服务器真装了会取走精灵的模组，也必须留得下痕迹。所以做一套持久化的异常记录 + 管理界面，照交易历史界面的形式。

**数据**：新增 `AnomalyState`（PersistentState + .bak，照 `FinanceState` 模式），每条：

| 字段 | 说明 |
|---|---|
| 时间 | 发生时刻 |
| 类型 | 租赁归还失败 / 待删除失败 / 战斗超时 / 快照恢复失败 |
| 涉及玩家 | 房东、租客（UUID + 名字） |
| 对象 | 精灵 UUID + 名称 |
| 详情 | 自由文本，写清"哪一步、期望什么、实际什么" |
| 已处理 | OP 可标记，界面上一键切换 |

保留最近 N 条（默认 500），超出时优先清理最旧的**已处理**记录；未处理的永不自动清理。

**告警渠道（三条并行，缺一不可）**：

- OP 在线 → 聊天框即时告警
- OP 离线 → 记录持久化；OP 下次登录时聊天框提示"有 N 条未处理异常"
- 界面 → 管理面板新增入口，列表 + 按类型/玩家筛选 + 标记已处理

**定位**：模组级通用异常系统，不局限租赁。第一批接入租赁三个点（归还找不到精灵、待删除找不到、战斗超时）；金融坏账等现有 OP 告警后续接入。

**入口与权限**：管理面板按钮，仅 OP；新界面记得补 E 键白名单。

## 已知残余风险

1. **精灵在租客手里被移出可控范围**（数据异常兜底）→ 租客在线时按 UUID 找不到 → 走"告警 + 暂缓归还"；租客离线时无法检查，直接归还，存在复制可能。**已查证 Cobblemon 1.7 官方无培育屋、牧场（Pasture）不拿走精灵**（`PastureLink` 绑定 pcId，精灵留在 PC 里），市面亦未见会取走精灵的附属模组——本条实际触发概率极低，防线保留是兜底。另：Cobblemon 没有统一的操作入口，第三方模组可直接读写 `player.party` / `PCStorage`，技术上做不到"只允许放 PC、其他一律拒绝"的白名单拦截。
2. **同 UUID 并存需实测**：租客离线期间，房东待领取有一只、租客存档里有一只，UUID 相同。Cobblemon 能否容忍需实际测试。若不行，备选方案是出租时给租客那只换新 UUID（快照保留原 UUID），代价是租客的精灵在 Cobblemon 眼里是新个体，需验证 PC 排序/图鉴无副作用。
3. **待领取有超期清理**：`cleanupOldReturns` 按 `pendingReturnRetentionDays` 清理超期未领取的归还精灵。房东长期不领会被清掉——属现有机制，租赁沿用。
4. **异常关服**：beta.1~6 全有的存档回滚窗口问题同样适用，验收时加异常关服测试。
