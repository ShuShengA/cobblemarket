# CobbleMarket 安全设计文档（中文）

> 本文档记录模组的经济安全防御机制与威胁模型。攻击面定义：**玩家通过客户端作弊、篡改/重放网络数据包、利用业务逻辑漏洞非法获取游戏资产**。

---

## 1. 核心架构原则

### 1.1 服务端权威
所有交易逻辑在服务器端执行。客户端只负责显示与发送操作请求，**任何客户端数据都不作为资产依据**：

- 货币余额：以服务端存储为准（Cobblemon Economy / CobbleDollars 服务端玩家数据 / 背包货币物品）
- 客户端仅缓存余额用于显示（BalanceCache），修改客户端内存不影响服务端账本
- 所有资金/物品变动都通过服务端校验并持久化

### 1.2 主线程串行
所有交易请求经 `server.execute` 进入服务器主线程队列**逐个执行**，不存在并发窗口：

- 两个玩家同时购买同一件商品 → 先到者成功，后到者按最新状态校验被拒
- 同一玩家重复发送同一请求（重放）→ 第二次处理时状态已被前一次更新，必然空手

### 1.3 状态扣减原子性
「校验 → 扣款 → 扣库存/发货 → 清账」在**同一个处理块内**完成，无中间态可被利用：

- 待收款领取：第一次处理后账本归零，重放第二次直接拒绝
- 待领取归还：归还成功后立即删除挂单记录，重放第二次无货可领

## 2. 防客户端伪造

| 数据 | 防御方式 |
|---|---|
| 上架精灵 | 客户端只发送精灵 UUID，服务端从 Cobblemon 存档（队伍/PC）查找**真实精灵数据**；IV/闪光/形态等一律不信任客户端上报 |
| 上架物品 | 客户端发送 NBT，服务端用 `fromNbtOrEmpty` 重建并对照**服务端真实背包**扣减，物品 ID 以服务端重建结果为准 |
| 购买价格 | 使用挂单的**服务端存储价格**，客户端不能改价 |
| 购买数量 | 服务端校验 `0 < count ≤ 挂单剩余库存` |
| 出价金额 | 服务端校验：> 当前价、加价幅度 ≥ 最低加价、出价后立即扣款 |
| 负价格/零价格 | 起拍价、上架价服务端校验必须 > 0 |
| 精灵伪造出售 | 上架瞬间精灵从存档移除，重复上架/重复出售同一 UUID 必然找不到 |

## 3. 资金安全机制

### 3.1 先校验后扣款
所有扣款前完成全部可失败校验（黑名单、价格限制、数量、库存、余额），避免「扣了钱才失败」。

### 3.2 退款兜底链
- 被超价：前出价者金额即时退回待收款（持久化）
- 自己连续加价：只净扣差价，不经过待收款
- 购买时背包放不下：全额退款，退不到的部分进待收款
- 结算入队失败：拍卖恢复 ACTIVE 待重试，不销毁资产、不重复转账
- 物品扣减防御分支：异常时退还已扣部分

### 3.3 账本一致性
- 待收款（pendingBalance）：服务端持久化账本，领取时「发钱 → 按实际发放量清账」
- 成交不变式：`currentPrice` 恒等于领先者累计净投入

### 3.4 数值安全
- 价格×数量用 Long 计算防 Int 溢出
- 手续费钳制 0~100%（超过会让卖家账本负数）
- 拍卖时长档位钳制 ≥1 分钟（0/负数导致上架即到期）

## 4. 业务规则防护

- **价格限制**：上架/起拍价校验（精灵按物种/V数/闪光；物品按单价×数量换算总价区间，堵住"多数量摊薄单价"的钻空子）
- **黑名单**：上架时校验，治理即时生效（含存量挂单购买时拦截）
- **封禁**：拦截一切交易操作（取回资产不拦，属于设计）
- **频率限制**：每玩家每操作 250ms 节流，防脚本批量请求
- **拍卖截止**：出价直接校验 `endsAt`，到期后任何出价一律拒绝（堵住反狙击复活漏洞）
- **反狙击**：结束前窗口内出价将结束时间重置到固定值（不无限累加）
- **并发上限**：每玩家活跃拍卖数上限（精灵+物品合计），客观限制全服拍品总量

---

## 5. 持久化与恢复

- 所有资产状态（拍卖、挂单、待收款、待取回、交易历史）即时 `markDirty` 持久化
- 服务器重启：进行中的拍卖按绝对时间戳正确续接，已扣出价款不丢失
- 结算完成即从状态移除（资产已转移），防止存档膨胀
- 存档损坏：`StateBackup` 校验 + .bak 恢复机制
- 本地 CSV 交易日志（中英双文件）作为额外审计记录

---

## 6. 威胁模型边界

**防御对象：玩家**（客户端作弊、封包篡改/重放、业务逻辑漏洞）——以上机制全覆盖。

**不设防的对象：拥有服务器文件/后台权限的人**（服主、被授权的管理员）。原因：

1. 物理访问 = 游戏结束：能改存档的人同样能拿到签名密钥、替换 mod jar、修改验证逻辑，任何防篡改签名都形同虚设
2. OP 在游戏内本身就有刷物品能力，防他们改文件没有意义
3. 这是运维层的信任问题（谁能碰服务器文件），不是模组层的技术问题

**结论**：模组的安全边界 = 防玩家。管理员级信任问题应由服主通过文件权限与选人管理解决。

## 7. 货币系统依赖边界

- **市场本身从不凭空产生货币**：所有资金变动都是账面流转（买家付款、退款、卖家收款），不存在"无中生有"的路径——刷钱漏洞永远不会来自市场代码
- **物品货币模式**（`cobbledollars=false` 且 `cobblemonEconomy=false`）：货币就是背包物品，完全由服务端权威的原版背包管理，零外部依赖风险
- **Cobblemon Economy 模式**（`cobblemonEconomy=true`）：货币由 Cobblemon Economy 模组管理，其 API 内部可按 main_currency 配置桥接到 CobbleDollars/Impactor 后端。若该模组（或其桥接后端）自身存在刷钱漏洞，市场无法识别"非法来源"的货币——这是上游依赖的信任边界，不是市场的缺陷
- **PCO 结算**（`cobecoCurrency=PCO`）：市场改用 PokeCoins 结算时信任边界同上——PCO 账本同样由 cobeco 管理，若 PCO 存在刷取途径，市场无法识别非法来源
- **镜像机制扩大信任边界**：装有 CobbleDollars 时 cobeco 会双向镜像两边余额（0.0.17 已实测）——任一上游存在漏洞，污染会经镜像机制扩散到另一侧；两侧余额一致不代表安全，只代表同步
- **CobbleDollars 模式**：货币由 CobbleDollars 模组管理，信任边界同上
- **应对**：服主发现货币模组漏洞时，可在配置中关闭对应开关（`currency.cobblemonEconomy = false`、`currency.cobbledollars = false`）切换回物品货币模式，市场功能不受影响

## 8. 历史漏洞记录（已修复）

| 漏洞 | 类型 | 修复 |
|---|---|---|
| 物品拍卖多数量摊薄单价绕过价格限制 | 业务逻辑 | 价格限制按单价×数量换算总价区间校验 |
| 过期拍卖被反狙击无限复活 | 时序逻辑 | 出价直接校验截止时间，不依赖节流结算 |
| 结算 15 秒节流延迟错开到期的拍卖 | 体验/时序 | 移除节流 |
| 结算入队失败资产销毁 | 异常路径 | 失败恢复 ACTIVE 重试，不转账不销毁 |
| 手续费 >100% 卖家账本负数 | 配置边界 | 配置加载钳制 0~100% |
| 物品拍卖上架不同步客户端背包 | 显示同步 | 补 markDirty + sendContentUpdates |
| 封包重放（理论） | 重放攻击 | 架构性免疫：主线程串行 + 状态扣减原子块 |
